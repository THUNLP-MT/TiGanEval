Give the nightly pass in `tilekit/sweep.py` a boundary setting, so the batch can render a tile the mosaic service will stitch to its neighbours, and so the passes already in the nightly list come back exactly as they came back before. The recorded nights under `project_records/` are examples of what this batch does, not the whole list of situations the finished pass has to survive.

Under any boundary rule other than `constant` -- `fill` included, whose out-of-range reads take the fill value exactly as `constant`'s do -- the kernel produces every cell of the field: border rows, border columns and corners included, each of them exactly once. No cell is left holding what the canvas started with, and no cell is written twice. On a `constant` axis nothing changes: a cell the window reaches past the edge for is not produced at all and keeps what the canvas already held.

Every out-of-range read has the result defined by `contract.map_index(length, index, mode)`, including its `None`, which means that access takes the pass's fill value rather than a cell of the operand. The pass accepts every name in the current frozen `contract.MODES`, and its observable results agree with the current frozen contract for `reflect`, `symmetric`, `fill` and the other names it carries. The tiles this batch renders are stitched against tiles the legacy renderer produced under the same rules, so a private reading of any of them puts a visible join through the mosaic.

The boundary setting is per axis. A single name stands for every axis and a list gives one name per axis in row-then-column order, and the two spellings of the same setting produce the same tile. Each axis is resolved with its own name before any cell is fetched, so at a corner, where both axes run past the edge at once, the two rules compose: the global swath wraps in longitude and holds at the poles, and its corner cells are exactly the cells four tiles meet at.

Boundary handling belongs to relatively indexed operands only. An operand named in the job's `standard_indexing` is addressed by its own coordinates, means the same thing at every cell of the tile, and is never moved by any boundary rule; a coordinate outside such an operand is refused rather than resolved to a cell that does exist, because a wrapped coefficient index quietly filters the region with the wrong number. A boundary setting the vocabulary does not contain, or one that does not carry exactly one name per axis, is refused at the start of the pass, before anything has been produced, so a frame buffer the mosaic service handed in comes back untouched. A frame buffer is the tile: the pass renders into the buffer it was handed rather than into a copy, which is what keeping one per region is for, so that buffer has to be the shape of the tile and has to hold the cell type the job declares. A job whose `output_dtype` is not the cell type of the buffer handed in for it is refused the same way, before anything is produced, and that buffer comes back holding what it held; the pass never quietly hands back a tile in the buffer's cell type instead of the declared one.

Everything the existing nightly passes rely on stays as it is. A `constant` job renders the tile it always rendered, with its fill value in the same margin cells; a job that spells out its own `neighborhood` gets that window and not the inferred one; a job that declares an `output_dtype` hands back a tile of that cell type even when its fill value is written as a float; and a job the mosaic service gives a frame buffer to writes only the cells it produces, so the rest of that buffer comes back holding what it held.

`tilekit/sweep.py` and `tilekit/edges.py` are the files to change. `tilekit/contract.py` ships in the mosaic service's release. You can inspect the project, replay the recorded nights and run your own experiments before you deliver.
