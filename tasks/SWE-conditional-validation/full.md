Finish the order platform's move from the hand-written pair checks in `orders/retiring_guards.py` to the `required_when` declarations the entity documents carry, so that a pair written into a document is the pair every service enforces and nobody has to remember which pairs exist. Each hand-written check covers only the pairs somebody got round to writing out, so they show how a pair binds and are not a statement of what a document asks for. The records under `project_records/` are examples of what the platform does, not an exhaustive list of the situations the finished write path has to survive.

The write path admits exactly the items the documents imply. A declaration binds on the controlling attribute's value, not on that attribute being present, and several values can make one pair binding, so an order paid by a method that owes no authorisation still goes through. The check runs on the item the parser hands on, so a value the document itself supplies satisfies a requirement rather than failing it. An attribute the document marks required stays required whatever its siblings hold. A declaration written inside a map is answered by that map's own attributes, never by an attribute of the same name at the top of the item.

A partial update commits exactly when it does not introduce a violation, and the store is what decides that. `build_update` is handed the change set and never the stored item, so a pair the change set could break becomes a condition the store evaluates against the item it already holds: setting a controlling attribute to a value that binds a pair must not commit while the dependent is neither in the same change set nor already stored; removing a dependent must not commit while the stored controlling attribute holds a value that binds it; a change set that touches neither side of any pair commits. Those conditions are written in the physical names the store holds, and they are added to the condition the caller already sent rather than replacing it, so a write whose own precondition does not hold still fails.

Change sets use logical paths. Setting a map replaces the complete map, while a dotted path changes only the named child; nested values are converted to their declared physical names before storage. Setting a path to `None` clears it and is governed exactly like an explicit removal. Therefore a whole-map replacement is held to every conditional pair inside that map, including fields omitted by the replacement.

Nothing the store already holds becomes unreachable or uncorrectable. The table has orders in it from before the current documents, some of them in states the documents would no longer admit, and every one of them still comes back from the read path carrying everything the table holds for it, under the names the document uses. A read the dashboard restricts to a projection returns that projection and does not fail because the attributes it did not ask for are the two sides of a pair. An update to an unrelated field on a record that already violates a pair still commits, and so does an update that repairs one, because what a write is held to is what it changes and not the whole state of the record.

A projection may name a map or a dotted logical path inside one. The result preserves the logical nesting, so projecting `route.mode` produces a `route` map containing `mode`, not a flat dotted key and not an empty result.

What the platform publishes says what the documents say. `to_contract` produces a document in which `protocol.validate_contract` accepts exactly the items the entity document implies, the same items the write path takes, which means the conditional pair is expressed as a conditional pair and neither dropped nor flattened into an unconditional required list. `to_dto` and `from_dto` carry a schema across a process boundary without losing anything that decides an outcome, so the reconciliation worker's rebuilt schema admits the same items and publishes the same contract as the one it was built from.

A declaration the store could not honour is refused when the document is written, with the `SchemaError` the platform already raises for a physical-name collision, and not accepted and quietly enforced against nothing. That covers a declaration naming an attribute that is not beside it in its own map, a declaration naming the attribute it is written on, a declaration inside a map naming an attribute at the top of the item, and a declaration on the key attribute, which is fixed at creation and always there. Every declaration the store can honour is accepted, including one whose controlling attribute is written further down the same document.

`orders/policy.py` and `orders/contract.py` are the files to change. `orders/protocol.py`, `orders/retiring_guards.py` and the documents under `orders/entities/` ship as they are. You can inspect the project, replay the records and run your own experiments before you deliver.
