Complete `ScopeManager` in `fulfilment/scopes.py` so that the workflow engine's data belongs to the state that declares it, whatever chart the engine is running. `fulfilment/protocol.py`, `fulfilment/engine.py` and `fulfilment/order_flow.py` stay as they are; `fulfilment/helpers.py` is yours. The recorded scenarios under `project_records/` are four runs this service has had, not the list of situations the finished layer has to handle: the claims team run their own chart on this engine, of a different shape and a deeper subtree, and it has to work there too.

Each state owns exactly the fields it declares, and a handler names a field rather than a state. A read or a write made in a state resolves along that state's chain, innermost first, so the innermost state that declares the name is the one whose data moves and the one the audit line names. A transition fills the bags of exactly the states it enters and drops the bags of exactly the states it leaves, which are the paths `Chart.entry_path` and `Chart.exit_path` give for it; every other active state keeps what it was holding. An internal transition runs its step and disturbs nothing. An external transition whose source and target are the same state leaves that state and re-enters it, so that state starts again. Once a state has been left the data it was holding is gone: `values()` no longer carries any of it, and a handler step that names that state is refused.

Every entry to a state gets its own copy of every default the state declares, including the containers. `Chart.declared` returns the declaration itself, shared by every piece of work the chart runs, so what an entry fills a bag with must be a copy of it and must be held on the running instance rather than anywhere the next instance can reach. What one run sees must not depend on how many other runs share the process or on how their events are interleaved: the same events for one piece of work produce the same data whether that work ran alone or in the middle of a shift. The chart the process started from is the chart it still holds when the last piece of work is finished with it.

Leaving a state that carries a resume point puts aside what that state and everything below it was holding at the moment it was left. Coming back in through that point restores what was put aside, as far down as the point reaches: a `full` point restores the whole subtree below its state, a `direct` point restores its state and its direct children and lets everything deeper start from its declared defaults. `Chart.resume_points`, `Chart.resume_state` and `Chart.resume_kind` say where the points are and how far each one reaches. A point holds nothing above its own state. A point declared partway down the tree puts aside that state and the subtree under it and nothing else, so a state the work walks back through on the way in that is above the point's state is an ordinary entry and starts from its declared defaults, whatever that state was holding when the work was put aside.

Handling one event produces exactly one `ChangeRecord` for each value that actually moved, carrying the state that declares the field, the field, the value before, and the value after. Filling a bag as a state is entered is such a movement, from nothing to what the bag is filled with, and dropping a bag as a state is left is such a movement too, from what the bag was holding to nothing. A write that stores the value already there has moved nothing and produces no record. The lines of one event reconcile against the run itself: for each state and field, what the run was holding when the event began, plus that event's lines for it, comes to what the run is holding when the event ends, with nothing standing in for a state the run was not in. The record set belongs to one event: `changes()` after an event holds that event's movements and none of the event before it.

A write is refused when the state it names is not active, when nothing on that state's chain declares the field, or when the value does not match the type the declaring state gave the field, in that order of checking. A refused write raises `ScopeError` with the matching code from `SCOPE_ERROR_CODES`, leaves the data exactly as it was, and adds nothing to the event's records. A step the layer cannot serve is turned away that way and in no other way, and the code it carries is the one that names what is wrong with it. A write the flow does allow is never refused.
