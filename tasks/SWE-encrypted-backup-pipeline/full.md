Finish the nightly archive job so that what lands in the two destinations is something the ops team can still get a database back out of, years later, with nothing but the runbook. The stretches of nights recorded under `project_records/` are examples of what the job meets, not an exhaustive list of the situations it has to survive.

An archive object is the night's dump compressed first and sealed second, laid out exactly as `restore_stream` takes one apart: the header `write_header` builds, the compressed bytes cut into chunks that are each sealed under the nonce `chunk_nonce` gives for their index of that object's stream, each sealed chunk behind its length in a `frame`, then `SENTINEL`, then `seal_trailer` over everything between the header and the sentinel. What the job hands a destination is therefore an object that `restore_stream` opens with the key its header names and that `decompress` then turns back into that night's dump, byte for byte. Sealing bytes nobody compressed is a different object: it costs the retention budget the three-to-one the window was sized on, and the runbook's second step has nothing to do.

Publication is the last thing a night does, and it is all or nothing. The key is resolved and checked before any destination object is opened, so a night with no usable key never creates one. An object is written, read back out of the destination it was written to, and only then finalized; a night that cannot get every destination that far leaves the window exactly as it found it, with nothing of that night's left anywhere and every object it opened closed. A night that does get there leaves exactly one finalized object of that night at each destination, and a night with a usable key that neither destination refused is a night that reaches both of them, whatever row the job files for it. The missing-backup alert cannot open an object, so an object of any size at the expected name is a night the alert will never page anyone about again.

The report the scheduler files is a measurement, not a claim. A night is `completed` only when the object each destination is actually holding comes back through the published read path and the decompressor as that night's dump; the check is made against what the destination is holding, never against the bytes the job still has in hand, because a destination that takes every write, reports nothing wrong and stores a short object is exactly the failure nothing else in the estate can see. A night that lands at one destination and not the other is a loss and is reported as one, a night that could have been archived and was not is a loss, and every night hands the scheduler a row rather than raising out of it.

A key configuration that names more than one place to look is refused rather than resolved: two sources are two answers, nothing on the host can tell which of them holds a generation the ops key file lists, and an operator restoring a year later cannot tell which one the job preferred, so no object is written for such a night at all. Every object that is published carries, in its header, the `key_id` of the generation that actually sealed it, and that generation is the one that night's configuration names — the retention window is longer than the time a retired generation survives its rotation notice, so a night sealed under yesterday's key is a night the ops key file cannot open by the time the drill reaches it.

The drill helper opens whichever night the drill picks out of the window, and it decides what an object is from the object rather than from its name. The window holds both eras at once — the sealed nights the platform archiver wrote before the filer went in and the plain compressed nights the job has written since — and the vault's tier move has left names that no longer match their contents in both directions. A sealed object is opened with the generation its own header names, taken from the key file the laptop has; an object that is neither an archive object nor one of the plain compressed dumps is refused with a diagnosis rather than turned into bytes that look like a dump and are not.

`nightly/pipeline.py` and `nightly/restore.py` are the files to change. `nightly/protocol.py` ships with the other two backup hosts in the platform release. You can inspect the project, replay the recorded nights and run your own experiments before you deliver.
