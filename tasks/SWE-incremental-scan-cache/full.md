Complete the incremental security scanner as a production CI component whose report stays trustworthy under configuration change, damaged storage, capacity pressure, and worker handoff. The recorded rehearsals in `project_records/` are examples of those conditions, not the full list of states the finished scanner has to survive.

An incremental run must report exactly the finding set that a full analysis of the same checkout under the same configuration would report. A file's findings depend on its exact contents and on the set of checks the configuration actually runs, and that set moves with the analyzer version, the profile, the selected and skipped checks, and the severity and confidence floors. A modification time is not evidence that contents are unchanged.

Saved cache data must never be trusted further than it can be confirmed. Stored entries can be truncated, overwritten with unrelated bytes, altered a byte at a time, found under a key that is not theirs, or reintroduced from a bundle taken before the code changed. Any entry the scanner cannot positively confirm still describes the file and the configuration in front of it must be treated as unusable and the file analysed again; “discarded” here means excluded from reuse, while the capacity policy separately determines when unused bytes are physically reclaimed. Damaged data and an unreadable import bundle must never stop a run and must never change what the run reports.

The persisted cache must stay inside the envelope the volume publishes. A run is handed its own instant in seconds and its expiry in days. After every run the store's total size must be at most the limit that run was given; that limit is one budget for the whole store, sized by how many files the tree holds rather than rationed one share per file, so a file whose saved result is several times an average file's belongs in the store like any other while the store as a whole fits. A generation the current run is using remains available until that run has formed its report; if all results the run could save do not fit together, the report must still complete correctly but the persisted store may omit some of them once the report is formed so that the hard limit is honoured. A generation the current run does not need becomes reclaimable once its age from production exceeds the configured expiry, and entries belonging to files that are no longer in the tree must also be reclaimed; serving a result does not refresh or rewrite it. Capacity pressure may additionally reclaim unexpired non-current generations, but when capacity is not in play a saved result for a file still in the tree stays until expiry, so a night that goes back to a configuration the pipeline ran earlier in the same window, with nothing edited in between, is served out of the store instead of analysing the checkout again. A run in which no file, option, or analyzer version changed must not rewrite the findings it is reusing, and that includes the first run on a worker warm-started from another worker's bundle, which must be able to serve those findings without writing them out again. When one complete current generation fits inside the published budget, a run that comes back to an unchanged checkout after a gap longer than the expiry leaves one saved result for each file in the tree and nothing else, and the clear-out keeps that generation so an immediately repeated run reuses everything regardless of the size of any one file's result.

An exported cache must be usable by another worker. Exporting the same cache state twice must produce identical bytes, and the transfer step re-exports a worker's cache every day it ships, so two exports taken on consecutive days with only a run that changed nothing between them are two exports of the same cache state and must come out identical. A bundle is a JSON object that declares its `format_version`; a bundle whose declared version is not supported must be refused without changing the receiving store, and refusing it must not raise. When a second worker holds the same code at a different checkout path with different file timestamps, importing a supported bundle must let it reuse every file's saved findings and report what a full analysis would report.

Every run's `cache_info` must describe what that run actually did: `total_files` is the number of files in the tree, `cache_hits` plus `cache_misses` equals it, `reused_paths` is exactly the set of files whose analysis was skipped, `cache_hits` equals its length, and `cached_entry_count` and `cache_bytes` equal the store's real entry count and total size when the run finishes.

`scanner/protocol.py` ships with the analyzer release and stays unchanged; `scanner/engine.py` and `scanner/exchange.py` are the pipeline's own code. You can inspect the project, replay the recorded rehearsals, and run experiments of your own before delivering.
