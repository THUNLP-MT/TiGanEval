Finish the shard planner so that a run of the suite is something the platform team can account for. The runs recorded under `project_records/` are examples of what CI does, not an exhaustive list of the situations the finished planner has to handle.

Across shard indices 1 to `shard_count` of one run, every file `discover` returns is assigned to exactly one machine. None is left out, none stands on two machines, none is listed twice on one machine, and nothing is assigned that is not in the tree — including when the shard count is larger than the number of files, when the history names files that a rename took away, and when the machines of one run are planned at different moments. Every machine comes back with a plan; a machine the planner cannot produce a plan for is a machine the runner will not start.

Within one run id, planning a machine yields the same set of files whether it is planned before any machine of that run has written its timings, after all of them have, or on a retry machine started after another run has published on top of them. The assignment is a function of the file set, the shard count, and the timings the run started with — the observations published at `RunContext.history_generation` or before — and never of the order this machine's walk of the tree returned the files in.

When there is no history file, when a killed job left one half written, and when nothing the history names is still in the tree, every machine's slice equals `hash_shard(files, index, count)` exactly, for every index. Damaged input is the case where there are no timings to use, never an exception: the run has to start.

That holds file by file on every other run too. A file the generation the plan names holds no observation of is assigned to `hash_shard`'s machine for it and to no other, however much of the rest of the tree that generation prices: the build cache and the quarantine list are keyed by shard index, so a file nobody has timed is a file whose index the run has no reason to change. Only a file that generation prices is moved by what it costs.

One run adds exactly one observation for each file that ran to completion, carrying the milliseconds that file took and the run's own clock reading, published in a generation later than the one the run started at. A machine's write keeps every observation the history already held, including when two or more finish callbacks overlap, so what the file holds after the run is the union of what all of them saw. The document's generation is the newest generation carried by its entries. A file the runner skipped and a file whose machine died part way through it get no observation, and no observation is invented for a file no machine completed. What a run leaves behind is a document `parse_history` can read.

Every plan carries what `require_plan` reads out of it: the run id and attempt, index and shard count from that invocation, the generation it was built from, the files it assigns, a price for each of those files, and a predicted total that is the sum of those prices.

A file's price is the time the history holds for that file at the generation the plan names — the newest observation published at or before that generation, which is what `timings_as_of` reads out of the document — and `UNMEASURED_MS` only where that generation holds no observation of it. Every plan of every run prices its files that way, including a plan on a run whose history covers part of the tree and a plan that leaves the split CI has always had alone: what the planner made of a timing is a separate question from what the plan says the history holds.

The split a plan produces is never slower than the same files under `hash_shard`, and on a run whose history covers every file in the tree no machine runs longer than 1.25 times the mean machine time.

On a run whose history prices only part of the tree the same line is held against what the plans themselves say: no machine's priced files come to more than 1.25 times the mean of what that generation prices the whole tree at, so a run that has timings uses them rather than leaving the split it could improve. The line is not held against a run one of whose priced files is dearer than the line itself, because no split of those prices sits under it.

`sharding/planner.py` and `sharding/support.py` are the files to change. `sharding/protocol.py` ships in the CI runner's release. You can inspect the project, replay the recorded runs and run experiments of your own before you deliver.
