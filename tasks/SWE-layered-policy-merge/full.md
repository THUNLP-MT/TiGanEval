Finish the ingress control plane so that a shopper stays on one pod for as long as the policies attached to their route say they should, and so that nothing the controller does on its own moves them. The drills under `project_records/` are examples of what the edge does, not an exhaustive list of the situations the finished plane has to survive.

The plan a push produces is the plan the attached policy documents compose to. Every key any attached policy names is in it and nothing else is, the proxy takes it rather than refusing it, and inside each kind the entries of the more specific policy come before the entries of the broader one. A fleet policy and a route policy attached to the same route both keep working: neither replaces the other, and a plan the proxy refuses is not a small mistake, because the route then goes on serving the last plan it accepted and the push looks to everyone like a change that never happened.

Each identifying key pins exactly once. Header names are compared the way the proxy compares them, so two spellings of one header name are one key; cookies and query parameters go by their name. That holds whether the repetition is two lines of one document or one key named by both attached policies, and the definition that survives is the one belonging to the policy that outranks the other by `protocol.rank`, with the fields the proxy uses for that kind: a header's rewrite, a cookie's lifetime, path and flags, and any step's `stop`. Fields that `protocol.Step` says the proxy ignores for that kind do not distinguish two definitions. A line repeated in a policy file is a line that changes nothing about where anybody lands.

A push of the same policy set produces the same plan and leaves every shopper on the pod they were already on. The controller reconciles the same routes many times a day and nothing about the storefront changes when it does, so neither the order it hands the attached policies over in nor the order the entries happen to be written in inside a document may reach the proxy. Where one policy's own entries sit among each other is yours to decide, as long as the same documents always compose to the same plan.

A policy that turns pinning off on a route clears the pinning that route would otherwise inherit, rather than merely adding nothing of its own; the route serves no plan at all and the proxy spreads its requests. A document that turns pinning off and also names entries is one the plane cannot apply as written: it is refused whole, through `protocol.admit`, so that the push does not go through half done and the route keeps the plan it already had.

The pin key of a request is the one the frozen contract defines. A step whose value the request does not carry contributes nothing to the digest, so an anonymous basket falls through to the next step instead of pinning on an empty value and instead of ending a walk at a step marked `stop`; a value is put through the step's rewrite before it is folded, so a session token that gains a rotating suffix does not move the shopper; the walk ends after a step that contributed and is marked `stop`; and a cookie's lifetime reaches the proxy as whole seconds through `protocol.ttl_seconds`, whichever of the two committed spellings the document uses.

`edge/compile.py` and `edge/pin.py` are the files to change. `edge/protocol.py` ships with the data plane. You can inspect the project, replay the recorded drills and run your own experiments before you deliver.
