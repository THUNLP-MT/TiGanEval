Complete the nightly catalogue loader in `loader/importer.py` so that the warehouse is trustworthy whether a load finishes, dies part way, is restarted, is handed the wrong export, is simply run again the next night, or is handed the next export upstream publishes. The recorded nights under `project_records/` are four nights this job has had, not the list of situations the finished loader has to handle. `loader/protocol.py` stays as it is; `loader/support.py` is yours.

The export defines exactly one correct catalogue. A row may join the warehouse only if it is admissible against the rows already admitted before it in the export's order, which is what `admit` decides. When the night's runs are over, the warehouse must hold exactly those admissible rows: none missing, none left over, none holding values other than the ones the export gives them. Every run must hand the scheduler a report rather than an exception: `SourceInterrupted` and `StorageFailure` are raised by the substrate and are the run's to catch, and a run that stops for one of them reports status `interrupted`. A run that reaches the end of its export reports `completed`.

No committed state may ever break the catalogue's own rules. Checking a batch after writing it is not enough: every transaction that commits must leave a database with no duplicate product code, no blank product code, no negative price, and no variant whose product is absent. Every inadmissible source row must be reported once, by its position in the export and with the reason `admit` gives for that row, and the reports of one night's runs must together account for every inadmissible row in the export.

Durable progress must be worth trusting. The upstream export is a retained stream: once a run has read to some position, the export only still holds the last `checkpoint_interval` rows behind that point, so work that is not durable by then can never be recovered by re-reading. A restart must carry on from what is durable rather than re-committing rows a previous run already committed, and the runs a night needs to reach `completed` must together write no more rows than the catalogue ends up holding plus one batch of `checkpoint_interval` rows for each run that stopped early. Progress recorded while loading one export must never be continued against a different one: such a run reports status `refused` and leaves the warehouse exactly as it found it.

The load must also stay inside the rest of the envelope the warehouse team publishes in `README.md`. It must commit its first batch after reading at most `checkpoint_interval` rows rather than holding the export first, it must never change more than `checkpoint_interval` rows in one transaction, and one run may open at most `ceil(total_rows / checkpoint_interval) + 4` transactions.

A finished load must settle. When a run reports `completed`, none of the loader's own bookkeeping may still be in durable storage. The next scheduled run of the same export must report `completed` and must leave the catalogue reading exactly as it did before that run. Upstream publishes one export a night into the same warehouse and the same store, always under the same file name, and the next night's export is usually a new one: the whole catalogue again with the day's new products in their place in the ordering, so the file name does not say which export a run was handed and a position taken from the previous export names a different row in this one. Rows admitted on an earlier night are repeated unchanged and are not removed by this feed; its daily changes are new products and their variants. The new export is nevertheless exact: the loader may neither add a row of its own nor change a published value. That export must load onto the catalogue the earlier nights left behind as if this loader had never run before, leaving the warehouse holding exactly the rows it admits.

You may inspect the project, replay the recorded nights, write experiments of your own against the workspace, and change the loader as often as you need before you deliver it.
