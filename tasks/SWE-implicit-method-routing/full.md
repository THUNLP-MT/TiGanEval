Complete the delivery portal's request surface so that it answers for itself about every path it serves, and changes nothing else about what those paths do. The stretches of partner traffic recorded under `project_records/` are examples of what the portal sees, not an exhaustive list of the surfaces the finished request surface has to assemble.

A size probe is the served GET response with an empty body. For the same path and token, generated HEAD must preserve GET's status and every header, including its original `content-length` and `content-type`, while returning `body=""`. The partner mirror uses that length to size the transfer. This applies to every outcome of the complete request pipeline:

| Where GET obtains its response | Generated HEAD status and headers | Generated HEAD body |
| --- | --- | --- |
| The operation succeeds | Identical to GET | Empty |
| The guard refuses the token (401 or 403) | Identical to GET | Empty |
| Path-value parsing rejects an id (422) | Identical to GET | Empty |
| The operation reports a missing record (404) | Identical to GET | Empty |

An empty response body never means resetting `content-length` to zero. Guard refusals and parsing errors are produced by `run_operation` before `Endpoint.handler` runs; they still need the same body-free response at the surface boundary. Removing a body only inside a handler cannot affect those earlier responses. The GET that defines the probe is the first GET the assembled table serves at that path. Its resolved `auto_head` setting decides whether the path has a generated probe; a later GET cannot enable one when the served GET has switched it off.

A path that has any operation with method lists switched on gets exactly one answer that describes it, and that answer is true. The methods it lists, and the `allow` field beside them, are precisely the methods the surface will serve at that path rather than refuse with 405 — gathered across every router that reaches the path, not just the router the answer happened to be made from, and counting both answers the surface generates for itself, the size probe and this description, since a caller that sends either of them is served — printed in the platform's own order. Its `operations` are the published catalogue's entry for that path with the two self-describing methods left out, so an operation kept out of the catalogue is absent from both and the partner platform's generated client and the path's own answer never disagree.

`auto_head` and `auto_options` are three-valued: a layer can switch a setting on, switch it off, or say nothing about it, and saying nothing is not the same as switching it off. The value that applies to an operation is the nearest layer that says something — the operation, then the mount that brought its router into place, then the router, then the service — so a setting written on a router reaches operations that are silent about it, a setting written at a mount overrides the router it is mounting, and an operation that switches something off keeps it off however loudly the layers outside it ask. When no layer says anything, a published read answers a size probe and no path advertises its method list. The same router mounted twice resolves once per mount: what one mount asks for never reaches the other, and mounting it a second time does not disturb what the router itself declares.

An operation written by hand for one of the two self-describing methods serves its path, and the surface generates nothing for that path and method. That holds whatever order the registration and the mounting happened in — whether the written operation came before or after the read it belongs to, and whether the two arrived through the same router or through two routers mounted at the same prefix. A written probe exists so that the cheap answer is the one served rather than the expensive read behind it. A path that has no written probe of its own still gets the one the surface generates.

Every request the surface answers with an operation it generated counts exactly once, against the mounted path it was served at and split by which of the two methods it was. Nothing else counts: not an ordinary read, not a probe or a description someone wrote by hand, not a channel opening that is not a request at all, and not a call at a path the surface does not serve. Because partners are billed per mounted path, one router mounted for two tenants is two lines and never one. What `usage_report` hands back is a copy the caller may write on, since the hourly job folds its own estimates into the mapping it is holding before it writes the report out.

`surface/routing.py` and `surface/metering.py` are the files to change. `surface/protocol.py` ships with the other services in the partner platform release. You can inspect the project, replay the recorded traffic and run your own experiments before you deliver.
