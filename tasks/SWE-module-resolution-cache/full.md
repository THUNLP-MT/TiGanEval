Finish the fleet's kit loader so that one kit file is one kit for a whole run, whichever job asks for it and however it spells the name. The stretches recorded under `project_records/` are examples of what a worker sees, not an exhaustive list of the situations the finished loader has to handle.

A kit file comes up exactly once per run. What the loader holds a kit under is the file's own identity — `FileStore.stat` of the path it resolved — and not the name or the path that reached it, so a relative path, a path through the `/srv/kits` link entry, a path with `.` or `..` in it, and a bare name found on the worker's kit path all reach the one kit the run already brought up. The licence desk is therefore billed once per kit file a run brings up, and a second `use` of a file already held costs no activation and no check. `reset()` clears everything the loader holds, because the worker process outlives one run and the next run has to read the store again.

Which file a name resolves to is a function of the directory of the file that asked for it, the worker's kit path, and the name; it is not a function of how that kit path happens to be spelled. Build the list of places to try as the asking file's own directory first and then the kit path's entries in the order the worker lists them, with each entry's surrounding whitespace and quotes taken off and any trailing separator dropped, so two workers whose settings differ only in spelling resolve every name to the same file. A name that carries a suffix is a path; a name without one is tried as `<name>.kit` and then as `<name>/index.kit`. Every relative name is resolved against the directory of the file whose body is running — the origin on the load context — and never against the job's directory when a kit is the one asking, so a job folder's own copy of a kit is what that job's own `use` reaches while a shared kit's `use` reaches its neighbour in the shared directory.

An activation that raises leaves nothing behind. The loader publishes what it holds only after `activate` has returned, so a kit whose body refused is not held, is brought up again the next time a job asks for it, and refuses again in the same way rather than being served from what the loader is holding; and the record of what is currently coming up is unwound on the failing path as surely as on the successful one. A file that is asked for while it is still coming up is a loop: raise `protocol.CycleError` carrying the run of kits from the one that is already coming up through to the one that led back to it, in the order they were asked for. `protocol.read_cycle_chain` is what the fleet reads that chain back with, so an entry written as the short name a `use` bound, as the store path the loader resolved, or as the file's identity label all name the one kit, and closing the run by naming the kit it started at again reads as the same chain; which kits and in what order is what has to be right. Nothing recurses without bound, and no kit whose body has not finished is ever handed to anything.

What a run ends with does not depend on the order the queue dispatched its jobs in. Every holder of a kit holds the one object, so a change one kit makes to another's table is seen by everything else that holds it, and a kit's body sees every kit it used already fully come up. The catalog a run ends with is therefore the catalog the kit files imply, entry for entry, whichever job first pulled a given file into memory. `cache_keys()` reports what the loader holds so that two nights of one job list report the one list: an entry names the file itself and not the path that happened to reach it first, and their order is one the schedule cannot move.

Loader diagnostics go to the job that caused them. Emit one line per event — a resolve, an activation, and a hit served from what the loader is holding — through the `Runtime` on the load context, built with `protocol.trace_line`, so it lands in that job's own log; nothing goes to the process console. Talk when the job's runtime settings carry a truthy `trace`, and equally when its invocation carries `--trace`, because the two are set by different teams. A job that asked for neither gets no lines at all. Every `use` a job made leaves the resolve line and then one more, the activation or the hit, so the hit path — where a loader that returns early usually says nothing — writes its two lines like every other ask.

`runtime/loader.py` and `runtime/support.py` are the files to change. `runtime/protocol.py` ships in the platform release and is the same file on every worker. You can inspect the project, replay the recorded stretches and run your own experiments before you deliver.
