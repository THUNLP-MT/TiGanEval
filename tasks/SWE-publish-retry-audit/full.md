Finish the release job's publishing step so that a release completes against a host that misbehaves and tells the truth about what it did. The releases recorded under `project_records/` are examples of what the console sees, not an exhaustive list of the situations the finished step has to handle.

Every file a host accepts holds the bytes the build made. The build outputs and the extra files the release carries are the same work and get the same treatment. A body is drawn from an artifact once and the host drains what it is handed, so a further try needs a body of its own: a try that hands over an already-drained body publishes an empty file that the host accepts and the release then reports as finished, which is worse than the file not arriving at all. A permanently refused, exhausted or stopped item may remain absent, but it never acquires a success line; every accepted item ends with the size and digest that `plan_items` said it was publishing.

The attempts block is what the vendor's support desk reconciles against their own log, so it equals what the host was actually handed. One line for every body that reached the host, none for anything else — opening a mirror bucket publishes nothing and is not a try — numbered from one for each file at each place, in order. An accepted item has exactly one success line, on the try the host took; an item the host never took has none. Every refused try carries the host's own words. `attempt`, `failure` and `report` are the shapes those lines take.

Outcomes are read through the frozen `classify_outcome`, and the three readings do different things. A status in `TRANSIENT_STATUSES` is the host's own weather and the file is offered again, up to the number of attempts the settings allow. Any other status the host chose is the host answering about this publish: a revoked token or a forbidden prefix is as final on the fourth try as on the first, so the file is not offered again and the host's own words go into the failures list where the person reading the summary will see them. The mirror answers with an error object rather than a status, so on that path the same distinction is the error's own `timeout` and `temporary` flags, and a mirror error claiming neither is an answer.

The pause before a further try is the configured delay, raised to the moment `parse_retry_after` names when the host supplies one, and then limited by `max_delay_ms`. The build-window cap is final: a host asking beyond it gets one capped pause rather than control of the whole release. A transient answer still consumes the normal retry budget after that pause. When the console's stop is set, no call leaves for the host: the stop is checked before opening a mirror or making a try and again after a pause, not only at the start of the release.

The release is a fact about the release and not about the order the console hands the files over in. The console gives them in whatever order the build finished them, and it differs from run to run. Two invocations from equivalent empty host state, given the same release and the same elapsed-time stop but different input orders, must therefore leave the same deterministic publishing prefix and the same attempts block. The step publishes in a settled order of its own rather than the one it was handed, and the block is put in the vendor's settled order before it is printed — by publisher, then place, then destination, then try number. It must actually begin work before a later stop, and one file's trouble does not decide whether a later file is published at all.

`publish/uploader.py` and `publish/support.py` are the files to change. `publish/protocol.py` ships in the toolchain release and `release.toml` belongs to the release manager. You can inspect the project, replay the recorded releases and run your own experiments before you deliver.
