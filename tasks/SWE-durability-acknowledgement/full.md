Finish the write path so the storage engine can say exactly what it has and what it has not: under group commit, under a device that refuses a write, when the node closes, and on a node with nothing attached to listen. The sessions recorded under `project_records/` are examples of what the pipeline does, not an exhaustive list of the situations the finished write path has to handle.

The sequence number the tracker publishes as durable is, at every point in a session, the highest one `protocol.recover` would return from the log as it stands: the highest whose record ends at or before the offset the device has taken. That includes the commits that asked for no fsync and rode along inside somebody else's, and it never decreases. Applying a record establishes nothing about the device; a record becomes durable when an fsync covers its byte range, and one fsync covers everything written below the offset it reports.

Nothing is released before the log holds it. At every point, the sequence numbers this write path has released — through a durability event delivered with no error on it, and through a parked client let go without an error — are among those recovery would return from the log at that point. That has to hold at every step, because the node can stop at any of them.

Exactly one durability event per commit that asked for an fsync, produced when the fsync covering it completes: never two, never none, and one even when the device refused the write, carrying that refusal. An event for a commit the device did take carries no error at all, because the feed releases a client on the event and holds it on the error. A commit that asked for no fsync produces none, and a commit whose fsync has not happened yet produces none. Each event carries its own commit's sequence number and correlation id, a size equal to `len(protocol.encode_batch(batch))`, and `protocol.key_count(batch)`. How many events the tracker has produced is reported as `durability_events` by `durability_stats()`, whether or not a listener is attached to receive them.

Every parked client is settled exactly once. `wait_for_durability(seq)` returns a `protocol.Waiter`, resolved with no error once that sequence number is durable and resolved with an error when it never can be, never twice and never left parked once the answer is known. A refused fsync latches: the first error the pipeline reports is what `durable_state()` carries from then on and is never replaced, the durable number stops where it was even though later fsyncs succeed and report a larger offset, and every client parked beyond that point is finished with that error instead of waiting for something that will never come. When the pipeline closes the node, every client still parked is settled with an error, and `pending_waiters` in `durability_stats()` is the clients actually still waiting, so it reaches zero.

None of this depends on the shape of the pipeline. A node with no durability listener registered behaves exactly like one with a listener: the same durable number at every step, the same clients released and refused, the same `durability_events` count. And the same commits produce the same outcome under any grouping of commits into fsyncs — the same sequence numbers released, the same clients settled the same way, the same number of events — whether the pipeline takes one commit per fsync, forty, or changes its depth in the middle of a session.

`engine/durability.py` and `engine/support.py` are the files to change. `engine/protocol.py` is shared with the replication feed, the recovery tool and the node console. You can inspect the project, replay the recorded sessions and run your own experiments before you deliver.
