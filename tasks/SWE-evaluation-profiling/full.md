Complete the rule report the decision service hands back, so that the platform can tell each bundle owner what their rules cost and the service still answers exactly what it answered before. The drills under `project_records/` are examples of what the service does, not an exhaustive list of the situations the finished report has to survive.

Switching the report on changes nothing about the decision it describes. For every request, the outcome and the sequence of expressions the engine evaluates are the same whether or not a report was asked for, so the report never re-runs a body to learn what it did, never forces a conjunct the engine short-circuits past, and never turns off the per-decision cache. Because a decision that spends more than `protocol.DEFAULT_BUDGET` work units is answered `indeterminate`, any extra evaluation also changes the answer on requests near that budget. The decision itself stays the one the bundle defines: the entry rule's value, `deny` when it has none, `conflict` when two definitions of one rule hold with different values, `indeterminate` only when the work really did run out.

Every row of the report is one rule definition of the loaded bundle, keyed by `protocol.definition_id`, so three definitions of one `allow` are three rows and two packages with an `allow` never collapse into one. A definition whose body the decision entered has a row, including a body that failed on its first conjunct and a body reached only through a reference from another rule; a definition the decision never entered has no row. A row's `successes` is the number of times that body ran to the end and produced its value, which is not the same as the number of times it was entered.

A row's `evals` is the number of times that body actually ran, counted when the body is entered and not when a reference to its rule is resolved. Reuse is counted separately: `reuse` is the number of times a reference to that rule was answered from the value the decision had already computed. The two together partition the references the decision resolved, so for every definition `evals + reuse` is the number of times that rule was asked for, and a rule read twenty times inside one decision reports one run and nineteen reuses rather than twenty runs.

A report belongs to the one decision it came from. It is created at the start of an evaluation that was asked for one, handed back on that decision's `Decision.profile`, and is `None` on a decision that was not asked for one. It does not accumulate across the requests a process handles, so the same request decided twice in one process produces two reports with the same numbers; it does not survive a bundle reload, so it never carries a definition the loaded bundle no longer has; and a report already handed over is not written into by any later decision.

The views built on top of a report preserve the run it came from. `package_totals` puts every row into exactly one bucket keyed by `protocol.package_of`, so the buckets sum to the run's own totals without writing into the report being summarized. `merge` adds two reports together row by row and returns one that shares no row object with either side, so a shard that has been merged still says afterwards exactly what it said before. `rate` is `protocol.success_rate` of a row's own counts, which is 0 for a row that never ran rather than an error.

`policy/engine.py` and `policy/profile.py` are the files to change. `policy/protocol.py` ships with the gateway. You can inspect the project, replay the recorded drills and run your own experiments before you deliver.
