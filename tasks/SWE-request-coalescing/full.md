Finish the summary relay in `relay/dispatcher.py` and `relay/sharing.py` so that callers who arrive at the same moment cost the backend one rendering without any of them being worse off for it. `relay/protocol.py` stays as it is. The four windows under `project_records/` are windows this relay has actually had, not the list of situations the finished relay has to handle.

Every caller the relay answers must be answered with exactly what a rendering made for that caller alone would have produced. The backend redacts a summary against the scope its principal's tenant and clearance make, so two callers may share a rendering only where a rendering for either of them would have produced the same text: a caller must never be handed a summary rendered for another scope. A caller that `runtime.is_authorized` does not admit for that document must be refused rather than answered. A caller that arrives after the backend has already sent some of its pieces must still receive the whole summary from its first piece, and a rendering that has already ended must not be handed to anyone who asks afterwards. Every rendering in flight comes back over one shared connection, which does not always hand a rendering's pieces over in the order the backend produced them; each piece carries the `index` it occupies in its own rendering, and a caller must be handed the pieces in that order rather than in the order they reached the relay. A caller attached to a rendering that died is owed that failure and not a summary.

Every call the front door accepts ends in exactly one answer, a summary or a refusal, and never in none and never in two. That holds when the shared rendering fails: a failure has to reach every caller attached to it, not only the one that started the work. It holds when the caller that started the work hangs up: the callers still attached to that rendering are owed their answer whatever the first one does. A caller that has hung up may be left unanswered, and no caller may be answered twice. And it holds for a call from a desk the directory no longer holds, which the front door accepts like any other: `runtime.tenant_of`, `runtime.clearance_of` and `runtime.is_authorized` raise a `RelayError` for a principal the directory has no entry for, and a callback that raises loses the caller it was handling, so a request path that reads the directory without allowing for that leaves the desk's connection open with nothing behind it. Refuse that caller. It has no tenant to bill it under, so whether it reaches the usage ledger is yours to decide.

One rendering per set of callers in flight for the same thing. Callers asking for the same document in the same scope while a rendering is running cost the backend exactly one, including a caller that arrives after the one that started that rendering has hung up; callers in a different scope, and callers who ask once a rendering has ended, each cost their own; and a document whose rendering failed must be renderable again for the next caller that asks, rather than staying marked as in flight. Every rendering the relay asks for belongs to a caller it is handling at the time: once a rendering has died the relay does not go back to the backend on its own account, because the desk's client carries its own `retry_budget` and decides for itself whether to come back. Answering a caller without the backend having rendered anything for it is as wrong as rendering twice.

The usage ledger gets one entry for every caller the relay answers, carrying that caller's own `call_id`, `principal`, `tenant`, `request_id` and `document_id` and the outcome it received, rather than the details of whichever caller happened to reach the backend. The words the entries use for a summary and for a refusal are yours to choose, but a desk that was refused must not be written down the same way as a desk that was shown the document. Finance bills and audit reads from those entries, so a caller answered from work started by somebody else still owes one, and a caller the relay never answered owes none: a desk that hung up before anything landed must not appear in the ledger at all. `statistics()` must be the relay's own count of what it did: how many callers it took in, how many renderings it asked the backend for, and how many callers it answered.

None of this may depend on the order the callers happened to arrive in, or on where the backend's pieces happened to land relative to those arrivals. Replay the same callers in a different order, or with the backend sending its pieces at different moments, and every caller must come away with the same answer it had before.

You may inspect the project, replay the recorded windows, write experiments of your own against the workspace, and change the relay as often as you need before you deliver it.
