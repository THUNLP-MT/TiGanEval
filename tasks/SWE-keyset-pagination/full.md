Complete the catalogue listing endpoint so that a client can walk the whole catalogue one page at a time, carrying nothing but a token, while merchandising keeps working in the catalogue underneath it. The scenarios recorded under `project_records/` are examples of what the service sees, not an exhaustive list of the situations the finished `find` has to handle.

The pages of one walk, put end to end over a catalogue nothing is editing, are the catalogue itself in the order that was asked for: the same products, in the same order, none missing and none twice. That is the order `list_all` gives, which orders by each named column in its direction, left to right, and separates products equal on every named column by ascending `item_id`. It holds for a single column and for several, ascending and descending in any combination, and it holds when a third of the catalogue shares one price — so the place a page reached is a place only when the id is part of it, because otherwise the products sharing the boundary's value are all skipped or all served again. The storefront's category pages have not moved off row counts, so a request that carries an `offset` and no token is still that window of the same ordering: the products after the first `offset` of it, at the size asked for. Every list is asked for by sort, so a request that names none is not a window of any ordering at all: it is refused through the `rejected` envelope the release ships, the way `catalogue_summary` refuses one it cannot order, and never answered out of the order the store happens to hold its rows in — with or without an `offset` on it, because the row count says where to cut a list and not which list it is.

Over a walk with additions and withdrawals between requests, while existing products keep their sort values and item ids are not reused, every product that is in the catalogue for the whole of the walk is delivered exactly once, and no product is delivered twice. Changes to non-sort columns are allowed; changing sort values during a walk is outside this guarantee. A product added part way through, beyond the place the walk has reached, and left in the catalogue, is delivered too — including one added at exactly the value the last page ended on, which lands after that place because the id separates it from the boundary. This is what makes the resumption a comparison of values against the catalogue as it stands when the request arrives, and never a row count, a position, an index into an earlier ordering, or anything the service remembers about how far this client had got. A product withdrawn ahead of the walk may simply not appear, and one withdrawn behind it changes nothing about the pages that follow.

A page carries a continuation if and only if at least one product exists after its last product under the current order, and the size of the page is the size asked for, clamped to `max_page_size` from `service.toml`, or `default_limit` when the caller asks for no size -- neither larger than that, which is what `max_page_size` exists to stop, nor smaller than it while products are still behind the page, which costs the phone a round trip per handful. Whether a continuation is offered cannot be inferred from the page having filled: a final page holding exactly the size asked for carries no continuation, and a page cut short by the clamp with products still behind it carries one. The clients read this literally -- they ask again while a continuation arrives and stop at the first page without one -- so a continuation on a finished list leaves a spinner turning against an empty round trip, and a continuation withheld from a page with products behind it hides the rest of the catalogue.

A token with an invalid payload or incompatible request parameters is refused, through the `rejected` envelope the release ships, and is never served, never raised as a fault out of `find`, and never quietly restarted from the first page. That covers a token sent with no sort, a token sent together with an `offset`, a token that cannot be read back, and a token minted under a different sort from the one the request asks for -- so the payload has to record the sort it was made under and `find` has to compare that against the request before it uses the place. It also covers an incomplete payload: a payload with a field taken out of it, and an empty payload, are both refused, as are boundary values that cannot be compared with the catalogue's sort values. The token is an opaque continuation format for clients, not an encrypted or authenticated credential; proof of issuance is not required. Refusal is the app's own recovery path; an exception out of `find` is not, because that reaches the client as a server fault. The contract runs the other way as well: a token this service did hand out, sent straight back on the request it was handed out for, is honoured, because that is how every customer reaches the second screen of a list.

Resumption is a pure function of the token, the catalogue and the sort. Nothing about a token is remembered inside the service, so the same token replayed against an unchanged catalogue produces the identical page from a service object built a moment ago, from the second instance behind the balancer, and from a process that has just started; nothing is bound to the service that minted it. That is what makes the token survive a redeploy, a fan-out across instances, and a client that keeps it in a query string overnight.

`listing/pages.py` and `listing/shelves.py` are the files to change. `listing/protocol.py` ships with the storefront and the reporting integration in the platform release. You can inspect the project, replay the recorded scenarios and run your own experiments before you deliver.
