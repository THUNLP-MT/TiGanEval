Complete the migration formatter so that running it over the schema repository is safe, repeatable, and reviewable. The recorded reviews under `project_records/` and the files under `migrations/` are examples, not an exhaustive list of what the finished formatter must handle.

Formatting must never change what a statement means. `parse_schema` is the authoritative reading: for every statement the formatter rewrites, the schema read from its output must equal the schema read from its input, the file must still hold the same number of statements in the same order, and the output must still be readable as DDL. Whitespace between tokens carries no meaning, but the text inside a quoted literal is a value: a comma inside `'First, Second, Third'` is part of that value, not statement structure, and a line break anywhere inside such a literal, at a comma or at a space, rewrites the column's default. Commas inside a parenthesised type such as `numeric(12, 2)` and inside a parameterised type such as `struct<a int, b string>` are likewise not statement structure.

Formatting must settle. Formatting a file the formatter has already formatted must produce that same file, formatting the same file twice must produce the same result, and two files describing the same schema in different layouts and capitalisations must produce the same output. Otherwise the formatter shows up as its own diff and nobody can separate a schema change from a reformat.

The comments that explain a schema must survive. Every comment in the input must appear once in the output, in the same order and with the same content under `protocol.comments`. A line comment must be the last thing on its line, because anything the formatter places after a `--` on that line is commented out and will not reach the database — including the opening parenthesis of a table whose author wrote the note on the line that names it. The schema review index keys annotations by physical output line and cannot join continuations, so a block comment must occupy one line of the output, however wide it is and however many lines its author spread it over.

The result must respect the directory's layout settings. No line the formatter writes may exceed the configured `line_width` while it still contains a comma the formatter could have broken at, and every line it indents must be indented by a whole number of the configured `indent`. A note or a quoted value that is itself wider than `line_width` has no such comma in it, so it stays on its one line rather than being wrapped.

Statements this formatter does not handle must be left alone and said so. `parse_schema` returning `None` marks a statement outside the supported shapes: it must appear in the output as the statement its author wrote, unchanged apart from the whitespace around it, and be reported with status `unsupported`, while every statement the formatter did rewrite is reported `formatted`. The report must carry one row per statement in the file, in order.

Keep `ddl/protocol.py` unchanged. You may inspect the project, replay the recorded reviews, run experiments of your own against the workspace, and revise the implementation before you deliver it for review.
