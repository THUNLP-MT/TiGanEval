Finish partner intake so that one field can be posted under more than one key without two keys ever becoming two answers. The runs recorded under `project_records/` are examples of what partners send, not an exhaustive list of what the finished loader has to handle.

The keys a field accepts are settled once, when its loader is built. A field accepts the key it is published under — the field id, with its trailing underscore trimmed where the configuration asks for that, spelled in `name_style` where one is set, and replaced outright by a `rename` entry where it has one — and, besides that, every spelling `aliases` lists for it and the field's own name in each style `alias_style` names.

A listed spelling is taken exactly as it is written: it is a key an outside system already spells that way, so `name_style` and the trailing-underscore trimming decide the published key and never touch it. A generated one is `convert_name` of the field's id in the named style, taken from the field's own name even where `rename` publishes that field under something else, because the fields most likely to need a spelling are the ones already renamed for somebody. Neither kind belongs on the way out: `dump` writes the record it is handed back out under the published keys and nothing else, carrying whichever fields that record holds, since not every record has every optional field filled in and the downstream readers have those names and no others.

Two fields never accept the same key. Where one would — a listed spelling equal to another field's published key, or equal to another field's listed or generated spelling — building the loader raises `ConfigError`, which is the one start-up failure the console can put in front of an operator, so they meet it against the configuration they wrote instead of one record at a time in production. A key one field accepts twice is not that case: a listed spelling equal to that field's own published key, and a generated spelling that comes out as the published key, are one key, and the loader builds and loads as usual. A blanket `alias_style` regenerates the published key of every single-word field, so refusing there would take the switch away from every real shape.

Each field's value comes out of exactly one key of the payload. Loading counts the accepted keys the payload carries for a field before it reads any of them, and where more than one is present the payload is refused with `AmbiguousKeysError` whose trail names those keys as the payload spelled them, and no record is built. That holds when the two carry the same value, for the reason `unwrap_payload` gives about the envelopes: nothing in the payload says which the sender meant to be the real one. A field with one accepted key present takes its value from that key; a required field with none is a `MissingFieldError`, and an optional one takes its default.

Every key in the payload is either consumed by a field or is one intake does not recognise, never both and never neither. The recognised set is every accepted key of every field, so under `forbid` a payload is refused only over the keys no field accepts, with the trail naming exactly those; and under `collect` exactly those keys are kept under `extra_in`, so a key some field accepts is never kept there and a key no field accepts is never dropped.

The two surfaces a partner sees stay faithful to intake. `input_schema` is the key-and-type catalogue: its properties are exactly every accepted key of every field, each carrying that field's `schema_property` fragment, and `required` is exactly the published key of each required field that has only one accepted key. It does not encode the whole-payload rules for multiple alternative spellings or `extra_policy`; intake enforces those when a payload arrives. When a value is wrong, the failure's trail carries the key the payload actually used, so the ticket support sends quotes back a key the partner sent.

`intake/mapper.py` and `intake/support.py` are the files to change. `intake/protocol.py` ships with the other services in the platform release. You can inspect the project, replay the recorded runs and run your own experiments before you deliver.
