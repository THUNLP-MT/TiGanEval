Finish the Kerbside handset's restore path so that a screen taken off the device is the screen the crew left, and so that taking one off the device is never mistaken for reaching the depot. The sessions recorded under `project_records/` are examples of what the handsets do, not an exhaustive list of the situations the finished restore path has to handle.

A query restored into a process that holds nothing for it renders exactly the screen its saved copy renders. The whole saved state is adopted: the rows, the error and its reason, the retry counter, both stamps, both update counts, the out-of-date mark, and, for a paginated list, the cursors its Load more reads. Nothing is recomputed from the moment of the restore, so the "last updated" line is the stamp the writer saved and not the clock reading the app opened at, and a screen that has never loaded is not marked as having loaded. Where a saved copy is not consistent with itself — a status saying one thing while the data and error beside it say another — the status is the one `status_for` gives for that data and that error, so a copy with no message in it puts no banner up and a copy carrying a message puts one up over its rows.

The background writer's save is part of the same path. A query screen visible immediately before `Persister.save` runs survives closing the app and opening a new process over the same device store, and restore then renders that same screen. A delivery cannot satisfy the restore contract only for snapshots that the console installed directly.

A restore produces no completed load. Over any session, the number of completed loads the app reports equals the number of calls that reached the depot: exactly one for each call that went out, and none at all for a screen the device answered. A persister that hands back a plain value is handing back the answer of the load that is running, and that answer goes through the completion path like any other, so a restored snapshot has to come back as something the driver can tell apart from a fetched value before it runs that path. Writing the state afterwards does not undo a completion that has already been reported. The same holds on the other side: start-up hands the rebuild the clock the app stamps from and the log the app reports itself through, and neither of them has anything to say about a query that came off the device, so a rebuild reports no completed load and takes no stamp from the clock.

After a restore nothing is running. The background writer saves whatever a query held at the instant it ran, so a saved copy can carry a load that was in flight or one that was waiting for signal; that load belonged to a process that has since gone. A restored query's fetch state is idle, and two saved copies that differ only in the load the writer caught restore to the same screen — the crew must not be shown a spinner with nothing behind it, and which instant the writer happened to run must not reach the screen at all.

The two ways into a screen agree. A cold open rebuilds every query from the device before anything is entered; a crew member tapping straight into one screen from the shift list restores that one query on its first load. For the same saved copy the two produce the same query and the same screen, which means the rebuild cannot use the rows-only write that structurally cannot carry an error, its reason, its counter or its stamps.

A rebuild over a query the process already holds moves neither stamp backwards. The rebuild is not guaranteed to have finished before the app's own first pull-to-refresh lands, so it routinely restores over live queries. The two axes are reconciled on their own stamps and separately: the rows, their stamp, their update count and the out-of-date mark come from whichever side saw the rows last; the error, its reason, its stamp, its update count and the retry counter come from whichever side saw the trouble last. The status is then what the surviving pair means, so rows the van has just pulled under an error the device saved afterwards is a banner over a list, not a clean success and not an empty error screen. Replacing the whole query with the saved copy loses rows newer than it; leaving the query alone because it exists loses an error the device recorded after those rows arrived.

`handset/persister.py` and `handset/adapters.py` are the files to change. `handset/protocol.py` ships in the app release and is the same file in the crew tablet and the depot's web console. You can inspect the project, replay the recorded sessions and run your own experiments before you deliver.
