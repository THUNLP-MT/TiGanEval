Finish the lineage audit over the record pipeline, so that the privacy office can take our report for the pipeline as it is written and the release gate keeps meaning what it meant. The drills under `project_records/` are examples of what the audit does, not an exhaustive list of the pipelines the finished checker has to survive.

Read on its own, one module says exactly what `protocol.reference_flows` says about it: the same exports flagged, at the same line and column, under the same check id. That covers every body of that file — a hand-off written inside a step and a method on a class in it are bodies of their own — every way a personal field enters a step, every form a value built out of one can take, the masking helpers that drop it, and the argument each sink actually sends, so that a payload assembled over several assignments is followed to the export and a sink whose table name or idempotency key happens to hold a personal field is not reported at all.

One leaking export is one row, keyed by `protocol.finding_key` at the export call itself. An export that two personal fields reach, or that is reached along two different paths, is still one row; an export inside a step that three other steps call is one row at that export and not one per caller; two exports written on the same line are two rows. Nothing is reported anywhere a value does not leave the company.

Which exports are flagged does not depend on how the pipeline is divided into steps and modules. Moving the construction of a payload into a helper, handing the value in as an argument, or moving the export itself into a step that is called from somewhere else leaves the report saying what it said before, whether the chain runs three steps deep or the steps call each other in a cycle. A step is handed whatever its callers pass it, wherever the call is written, including from a hand-off inside another step. And a step that some other caller hands a personal field does not thereby make this caller's value personal: what a step hands back carries a personal field when its own body builds one, or when this call passes one into an argument the step builds its answer out of, so a line builder three steps share reports the caller that hands it a subject's address and not the caller that hands it a region.

The report does not depend on the order the checkout hands the modules over. The same set of modules presented in any order returns the same rows in the same sequence, which means the whole pipeline is read before any export is judged rather than module by module as the modules arrive, and the rows come back in the order `protocol.require_report` reads.

The rows the audit already had stay exactly as they were. `protocol.baseline_findings` for every module of the pipeline is in the report, at the same lines and under the same check id, with the new rows added beside them. A line that now carries both an existing row and a new one carries both.

`lineage/tracer.py` and `lineage/summaries.py` are the files to change. `lineage/protocol.py` ships with the triage console. You can inspect the project, replay the recorded drills and run your own experiments before you deliver.
