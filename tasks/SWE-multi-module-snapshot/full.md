Finish the plugin sandbox's dump tool so that a dump says what the sandbox held at one moment and a restore puts that moment back. The runs recorded under `project_records/` are examples of what the sandbox does, not an exhaustive list of the situations the finished tool has to handle.

Every plugin in one dump is read at one epoch of the host, and the dump records the epoch it names. The host does the pipeline's queued work whenever an arena is touched, so a walk that asks each plugin what it is holding right now can cross several moments. A dump interrupted between two of its per-plugin reads has to hold the same bytes as one that ran with nothing else going on, and its recorded epoch and returned arenas must agree.

What a dump holds is fixed at the moment it is taken. Later pipeline work must not change it, and every reading of an arena from the dump must be an independent writable buffer: changing one returned buffer changes neither the dump nor what the next reader receives.

An incremental dump taken against any baseline, including another incremental, reads back for every plugin as the whole arena at its own epoch, equal to what a full dump at that epoch would hold. Its persisted debug-volume representation for each plugin is `delta(key)`: exactly `diff` of the image its baseline reconstructs to against that arena. `image(key)` is the reconstructed view and is not separately persisted. That holds for a plugin whose arena grew, one whose arena shrank, one the loader put somewhere else in `host.plugins()` after a reload, one that is new to the dump, and one that did not change at all. A dump covers exactly the plugins it is handed. The console can load and unload plugins while a batch is running, so a plugin new to the dump is diffed against an empty image, while a plugin no longer handed to the dump is absent; neither change stops the dump being taken.

Every plugin the dump holds has to still be there among the targets it is offered back to. Each offered target must be the exact object currently present in `host.plugins()`, not an uninstalled lookalike with the same key, layout and capacity; it must carry the layout it carried when the dump was taken, be loaded rather than detached, and have capacity for the bytes the dump holds for it. If any one of those does not hold, the restore raises `RestoreRefused` with its `reason` set to the matching code (`duplicate`, `missing`, `detached`, `foreign`, `layout` or `capacity`) and its `plugin` set to the blocking key, while no plugin's `write_seq` moves. Those are the only reasons to refuse: a matching plugin in a smaller block that still holds the bytes is restored, and a plugin loaded since the dump was taken is left alone. A restore that goes ahead writes to exactly the plugins the dump holds, once each.

After a restore that went ahead, each plugin's arena is byte for byte the arena the dump recorded, and it is exactly that long: bytes written past the recorded length after the dump was taken are gone rather than left behind as a tail. The roll-up and meter arenas then add up to what the loader declared, so `PluginHost.balance` reads the batch the dump recorded.

`plugins/coordinator.py` and `plugins/support.py` are the files to change. `plugins/protocol.py` ships in the pipeline release and is the same file in every ingest worker. You can inspect the project, replay the recorded runs and run your own experiments before you deliver.
